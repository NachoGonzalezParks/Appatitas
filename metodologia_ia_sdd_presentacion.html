Contexto operativo

Tenés un tablero en Trello, una instancia de OpenCode y Cursor abiertos. El producto es una aplicación orientada a productos y servicios para mascotas. El objetivo no es “usar más IA”, sino definir un sistema repetible: qué documentás, en qué orden lo pedís y cómo verificás el resultado antes de acumular deuda técnica.

Escala por módulos

Cuatro ramas de negocio conviven en el mismo ecosistema; el diseño permite sumar dominios sin reescribir el núcleo.

Spec antes que código

SDD separa qué se construye, cómo y en qué tareas; la IA deja de improvisar y el repo conserva el criterio.

Trazabilidad total

Prioridad en Trello; decisiones técnicas en markdown versionado; comportamiento fijado con pruebas.

Visión del producto en cuatro ramas

Convivirán en el mismo ecosistema; el diseño debe permitir integrarlas por módulos o bounded contexts.

1) Rama clínica (portal)
  • Carga de tutor
  • Carga de veterinario como historia clínica
  • Buscar veterinario en proximidad
  • Vacunación y desparasitación
  • Registro de mascotas
2) Rama alimentación y productos
  • Servicio puerta a puerta de alimentos, snacks, comidas, etc.
  • Ropa, juguetes, accesorios
3) Rama servicios
  • Peluquería, paseos, traslados, guardería, educación canina
4) Rama adopción y búsqueda
  • Adopción y tutores
  • Perdidos y encontrados

Foco actual y principio de escalabilidad

El trabajo inmediato se concentra solo en la rama 1 (clínica / portal). Aun así, la arquitectura y el repositorio deben permitir sumar las otras ramas sin reescribir el núcleo: módulos con límites claros, contratos entre dominios (API o eventos), datos que no se mezclen por conveniencia y carpetas o paquetes que reflejen dominios, no solo “features sueltas”.

Resumen: construís el primer módulo completo y bien acotado; dejás interfaces y convenciones listas para que alimentación, servicios y adopción se enchufen como extensiones, no como parches.

Rol de cada herramienta

  • Trello: backlog visible, estados, prioridades, definición de “hecho”. Es la capa humana y de compromiso.
  • Cursor / OpenCode: ejecución asistida: specs, planes, código, refactors, tests. No reemplaza la decisión de qué construir.

Si todo vive solo en el chat, perdés trazabilidad. Si todo vive solo en Trello sin artefactos técnicos, la IA improvisa. El equilibrio es: decisión y prioridad en el tablero; especificación y código versionados en el repo.

SDD: flujo y artefactos

SDD (Specification Driven Development) evita el uso desordenado de la IA: contexto persistente, código consistente y un camino para escalar (incluido el uso futuro de agentes especializados).

IDEA → SPEC → PLAN → TASKS → CODE → REVIEW → TEST

Archivos sugeridos (o equivalente en tu repo)

  • spec.md — Qué se construye: alcance, reglas de negocio, fuera de alcance, criterios de aceptación.
  • plan.md — Cómo se construye: capas, módulos, modelo de datos de alto nivel, riesgos, orden de implementación.
  • tasks.md — Checklist ejecutable: ítems pequeños, verificables, enlazables a commits o tarjetas de Trello.

Problemas que resolvés con este orden

  • Uso desordenado de la IA y prompts contradictorios.
  • Falta de contexto persistente entre sesiones.
  • Código inconsistente por mezclar diseño e implementación en un solo pedido.
  • Dificultad para escalar a más ramas o a más personas.

¿Centralizar todo el desarrollo en un solo asistente?

Podés usar un único entorno (por ejemplo OpenCode o Cursor) como “mesa de trabajo” principal para crear y modificar archivos, siempre que el criterio de verdad siga siendo el repositorio y los artefactos (spec, plan, tests), no la memoria del chat.

No conviene depender de una sola conversación lineal como única fuente de verdad: se pierde contexto, se repiten errores y es difícil auditar cambios. Lo que sí tiene sentido es un flujo centralizado: un solo lugar donde versionás decisiones (markdown en el repo + tarjetas en Trello) y desde ahí invocás a la IA con contexto explícito (@archivos, fragmentos de spec).

Si más adelante usás varios agentes (planificador, implementador, revisor), el SDD ya deja el cableado conceptual: cada rol consume y produce artefactos distintos, sin mezclar roles en un solo prompt gigante.

Siguiente paso recomendado

  1. Escribir una spec mínima solo para rama clínica: actores (tutor, vet, mascota), flujos críticos, datos que cada uno puede ver o editar.
  2. Derivar un plan técnico en una página: módulos del repo, límites entre identidad/tutores/mascotas e historia clínica, y cómo integrar geolocalización de veterinarios sin un solo agregado acoplado.
  3. Partir tasks.md en bloques de una tarjeta de Trello cada uno (o checklist en la tarjeta), con criterio de hecho testeable.
  4. Acordar reglas de repositorio: nombres en español para funciones y esquema de base de datos; tests junto al código (TDD).
  5. Solo entonces pedir implementación asistida por IA, citando spec, plan y tarea actual en cada sesión.

Cómo mejorar los prompts

Un buen prompt incluye: rol, objetivo, restricciones, formato de salida y qué no hacer. Separá “pensar arquitectura” de “escribir código”; si mezclás, obtenés código prematuro o specs vagas.

Ejemplo: spec (sin código)

Rol: arquitecto de producto y dominio veterinario simplificado. Contexto: aplicación modular para mascotas; ahora solo rama clínica (portal). Objetivo: redactar spec.md para "registro de mascotas y vínculo con tutor", incluyendo reglas de negocio y criterios de aceptación. Restricciones: no escribir código ni SQL; no incluir ramas 2–4 salvo menciones de extensibilidad en una sección breve al final. Salida: markdown con secciones Alcance, Actores, Flujos, Datos, Errores esperados, Fuera de alcance.

Ejemplo: plan (sin código)

Rol: arquitecto de software. Entrada: adjunto spec.md de registro de mascotas y tutor. Objetivo: generar plan.md con módulos, modelo conceptual de datos, endpoints o casos de uso, y orden de implementación. Restricciones: no generar código; no inventar integraciones externas sin marcarlas como hipótesis. Salida: lista ordenada de decisiones técnicas y riesgos.

Ejemplo: tareas

Convertí plan.md en tasks.md: checklist de ítems de menos de 2 horas cada uno, con ID estable (T1, T2, …) y criterio de verificación por ítem.

Ejemplo: implementación (con código)

Implementá solo la tarea Tn del tasks.md. Respetá nombres en español para funciones y tablas. Incluí o actualizá tests que fallen antes de pasar. No modifiques archivos fuera del módulo clínica salvo imports necesarios.

Para iterar prompts en el chat, aportá spec o fragmento vigente, error o diff concreto, y restricción exacta (por ejemplo solo backend o solo UI).

Reglas de uso correcto de la IA

  • No improvisar flujo: seguí SPEC → PLAN → TASKS antes de pedir código masivo.
  • No mezclar roles en un solo mensaje (diseño + implementación + estilo + deploy).
  • No generar código sin contexto versionado al que la IA pueda anclarse.
  • No código sin spec; no cambios grandes sin plan; iteración en pasos verificables.

Arquitectura modular (recordatorio)

Clínica, productos, servicios y adopción son contextos distintos. Mantené interfaces claras y separación que permita agentes o equipos trabajando en paralelo más adelante.

Cierre

La herramienta concreta (Cursor u OpenCode) importa menos que el sistema: artefactos claros, prioridad visible en Trello y código con pruebas que fijen el comportamiento. Eso sostiene el aprendizaje y la escala a las otras ramas.
